2FRD — Functional Requirements Document

2.1 Latar belakang dan tujuan bisnis

Toko online kecil–menengah butuh sistem yang tidak pernah menjual barang melebihi stok, tidak menagih dua kali walau koneksi pelanggan buruk, dan tetap cepat saat promo. Aplikasi ini dibuat sebagai portfolio yang menunjukkan cara menyelesaikan masalah-masalah tersebut secara benar, bukan sekadar CRUD.

  • BO-1 Pelanggan bisa belanja dari HP: lihat katalog, keranjang, checkout, bayar, lacak pesanan.
  • BO-2 Stok dan uang selalu konsisten, termasuk saat ribuan pembeli berebut barang yang sama.
  • BO-3 Admin bisa mengelola katalog dan memproses pesanan tanpa akses database.

3.5 Keputusan arsitektur (ADR)

IDKeputusanAlasan
ADR-01Modular monolith, bukan microservicesSatu tim, satu database, butuh transaksi lintas modul (order + stok + cart). Batas modul tetap jelas lewat package dan interface.
ADR-02Conditional UPDATE untuk stokUPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?: atomik tanpa lock tabel; plus CHECK stock >= 0 sebagai pertahanan terakhir.
ADR-03Lock ordering saat checkoutProduk dikunci berurutan menurut product_id supaya dua checkout yang berbagi produk tidak deadlock.
ADR-04Harga snapshot di order_itemsDenormalisasi disengaja: perubahan harga atau penghapusan produk tidak mengubah pesanan lama.
ADR-05Idempotency-Key + partial unique indexUnique index pada idempotency_key dan (order_id) WHERE status='PENDING' menjamin satu pembayaran aktif per pesanan, bahkan saat race.
ADR-06Refresh token rotation + SHA-256Token tidak disimpan mentah; reuse token lama mencabut semua sesi user.
ADR-07Cache-aside, fail-openRedis mempercepat baca; kalau mati, API tetap jalan dari database (terbukti di stress test).
ADR-08Riverpod 3 tanpa codegenSesuai requirement lowongan; DI dan state dalam satu sistem, mudah di-override di test.
ADR-09Uang sebagai integer rupiahBIGINT di DB dan int di Dart; tidak ada float untuk uang.

3.6 Keamanan

AncamanMitigasi
Pencurian password dari DBbcrypt cost 12
Token refresh bocorDisimpan sebagai hash SHA-256, rotasi tiap pemakaian, reuse detection mencabut semua sesi
Akses data user lain (IDOR)Kepemilikan dicek di service; pesanan orang lain dibalas 404, bukan 403
User biasa memanggil endpoint adminMiddleware RequireRole(admin) di server; UI admin hanya kenyamanan

7.6 Analisis

  • Baca katalog memenuhi target dengan jauh. Detail produk dari cache mencapai 23.006 req/detik dengan p95 5,3 ms. List lebih berat (6.304 req/detik) karena respons 20 produk diserialisasi ulang.
  • Login sengaja lambat. Satu verifikasi bcrypt cost 12 butuh ±226 ms per core; 2 core → maksimum teoretis ≈ 8.8 login/detik, terukur 8,9. Ini fitur keamanan (memperlambat brute force), bukan bug. Kapasitas login naik linear dengan jumlah core.
  • Endpoint terautentikasi (GET /cart) 2.802 req/detik: verifikasi JWT + 2 query dengan preload, dibatasi pool 25 koneksi DB.
  • Titik jenuh sekitar c=200: CPU mesin habis (server dan load generator berbagi 2 vCPU). Tidak ada error atau timeout sampai 400 koneksi; antrean memanjang secara wajar.
  • Konsistensi terjaga di bawah tekanan: tidak ada overselling, tidak ada pembayaran ganda, tidak ada pesanan ganda, tidak ada deadlock.
